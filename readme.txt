Интеграционная платформа 

Есть данные продукты-источники. 
Продукт-источник - это информационная система, которая генерирует какие-то данные, либо эти данные получается из каких-то систем, 
и далее эти данные хранятся в реляционной СУБД (PostgreSQL), продукт-источник отправляет данные в Kafka () и продукт-источник отправляет 
данные в REST API (есть endpoint и спецификация). 
Аналогично для продуктов-потребителей

Основная проблема:
В большой экосистемной компании существует множество продуктов с различными интеграционными интерфейсами. Чтобы обмениваться данными 
и строить на основе данных новые бизнес-процессы или развивать стратегические инициативы, продуктам нужно интегрироваться. 
Создание интеграции между продуктами, которые уже находятся в промышленной эксплуатации, треубет много ресурсов, такие как 
стоимость команды, большое количество трудозатрат по времени, дополнительные инфраструктурные ресурсы.
Более того, у двух и более интегрируемых продуктов имеются разные публичные интерфейсы для интреграции, т е у одного продукта только 
API, а у другого только кафка, у третьего только СУБД. 
Таким образом, в любом случае требуются значительные доработки в одном или нескольких продуктов.

Интеграционная платформа
Должна выполнять роль прослойки. Это масштаблная реализация подобных паттернов (адаптер, масады), 
т е в платформе есть готовый набор адаптеров, где можно прийти и накликать нужный адаптеров для того, чтобы было соединение 
публичных интерфейсов).

API backend
Есть владелец продукта (продуктов-источников), он хочет зайти в API backend и сказать, что хочет опубликовать свой публичный интерфейс
в нашу интеграционную платформу и дальше подхватывает эта API backend, которая дальше дергает другие микросервисы, которые 
позволяют опубликовать эти публичные интерфейсы, а дольше когда придет владелец продукта (продуктов-потребителей) и скажет, что хочет
подключиться к этому публичному интерфейсу. Как работает: API backend должно работать как на подписку, так и на подключение.
В целом, можно декомпозиторвать на отдельные микросервисы, например, API backend публикации, API backend подключение/подписка.
Дальше API backend публикации принимает схему, параметры подключения и дальше сохраняет интерфейсы в СУБД (сохранить инфу о подключении
к источнику по таблице на каждый интерфейс). Дальше, когда приходит владелец продукта и хочет поискать каждый интерфейс, то должно быть 
API backend поиск интерфейсов. Поиск будет существляться по продукту и перечню его интерфейсов. Далее владелец продукта-потребителя 
находит нужный интерфейс, нажимает кнопку подключиться и срабатывает API backend подключения, далее API backend подключения
идет в субд хранения интерфейсов, находит нужную информацию для подключения, и в движок дает команду о связки двух интерфейсов, причем указывается
при подключении информацию о потребителе (она также хранится в СУБД)

Далее в движок по кафке передается информация и том, что произошло подключение интерфейсов с помощью CDC - Change Data Capture - захват измений в СУБД. Реализуется в технологии debezium
В движке используется cronjob, чтобы передавать данные по расписанию
